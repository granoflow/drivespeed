# 缓存测试计划：搜索、模型知识、1 TiB 兜底

当前执行模型（包括其宿主提供的工具）负责研究与判断，Python 只验证输入、计算计划和执行。先复用同设备有效的本地网络参考缓存；缺失或过期时再走以下研究/降级顺序。缓存复用不重置查阅日期。不是让测速脚本另建模型客户端。

1. 每次识别所选硬盘的准确型号与容量。能用网络搜索时先查厂家规格、同容量实测的持续写入曲线；区分伪 SLC 写缓存与 DRAM，不能把 2 GB DRAM 当作数百 GB 写缓存。记录实际打开的来源、发布日期/查阅日期、测试条件及冲突。厂家未公开缓存容量时明说，第三方实测只作规划估计。多个结果取合理偏保守的值，不照搬其他容量型号。
2. 所选模型及宿主没有实际搜索工具时，先让模型自查记忆，再考虑 `model_knowledge` 估计。必须能明确说明记得的是哪一准确型号和容量、哪一种写缓存、具体数值/范围的回忆依据，并检查是否与自己掌握的规格及测试条件矛盾；排除把其他容量版本、其他产品、DRAM 或主机内存当成写缓存。仅说“我很确定”、给出自评置信度，或只用 TLC 总容量除以三，都不足以确认没有记错。将这次核对过程简要写入 `knowledge_basis`，不得虚构查阅、来源或验证过程。

   只要模型记忆模糊、无法排除型号/容量/缓存种类混淆，或给不出具体依据，就不得输出知识估计，直接进入 1 TiB 兜底。模型自查不能保证事实正确；通过自查的值仍标为模型知识估计，而不是已核实参数或实测结果。无需为了避免兜底而强行补出一个数字。
3. 两条路径均没有可用估计时，脚本按 1 TiB 制定兜底请求量。它是测试计划，不是“这块盘有 1 TiB 缓存”的判断。

有估计时，计划写入量为：估计写缓存＋max(32 GiB, 缓存的 25%) 不确定性余量＋max(64 GiB, 90 秒预计降速后写入量)。后 90 秒用于降速后的 30 秒继续写入及 60 秒稳定采样；期望速度由资料或模型知识给出，若有当前链路实测写速，则两者取较低值。无速度估计时用缓存的 50% 估计后续写入量。该公式只决定硬上限，满足实测停止条件仍提前停止。

空间不足时下调文件与写入量，保留至少卷容量 10%、10 GiB、测试文件 25% 的空闲空间，在计划中记录 `limited_by_space_or_budget`；不能声称缩小后仍一定覆盖缓存。时限仍默认 1800 秒。用户明确指定的文件、写入和时间上限优先。

如果资料显示缓存后原生速度不低于当前链路实测写速，标记 `interface_may_mask_cache`。此时接口/主机路径可能掩盖缓存变化，不能靠持续增加写入保证识别缓存；应向用户解释可观察性限制，必要时改用更快连接或仅将参考值列为参考。

## 结构化输入

将研究结论保存到本次私有任务目录，用 `--cache-estimate-file /absolute/path/estimate.json` 传给 `--profile cache`。数据只用于规划；测出的缓存容量与速度在 `cache_assessment` 中单独记录，不相互覆盖。

```json
{
  "basis": "web",
  "drive_model": "与当前系统检测一致的型号及容量",
  "cache_bytes": 107374182400,
  "sources": ["https://example.com/actual-reviewed-source"]
}
```

上面数字是独立的格式示意，不能作为任何硬盘默认值；可选 post_cache_mb_s 与 host_write_mb_s 只填写本次资料或当前实测得到的速度。`basis` 只接受 `web` 或 `model_knowledge`；后者 `sources` 可为空，但必须提供非空 `knowledge_basis`，说明具体回忆依据与型号/容量/缓存类型的自查结果。脚本只校验记录存在，不能证明模型记忆正确；是否有实际依据由执行模型按上述标准判断。`cache_bytes` 为正整数字节，速度字段可省，必须用十进制 MB/s。脚本重新识别当前设备，型号与规划文件不匹配时拒绝使用。不要把研究文件里的期望值伪装成测速结果。

无可靠估计时省略此参数即采用 1 TiB 兜底。先 dry-run 查看实际文件空间、累计写入上限、来源与硬上限，再按当前用户授权执行；不要求用户机械选择固定档位，不绕过已明确的写入限制或本地确认约定。
